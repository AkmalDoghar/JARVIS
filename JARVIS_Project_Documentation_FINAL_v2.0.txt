1. PROJECT OVERVIEW

Project Name: JARVIS

Goal: Build a personal AI assistant for Windows that can understand
natural language and voice commands, answer questions, use the internet,
control the computer, work with files and code, understand the screen,
remember useful information, and perform multi-step tasks safely. It
should keep working (with reduced abilities) when the internet is not
available.

This project is inspired by the concept of Iron Man's JARVIS, but the
implementation will be a practical personal AI agent rather than a
fictional system.

IMPORTANT: We will build JARVIS in phases. We will NOT try to build
every feature at once.

Realistic expectations:
- JARVIS is software running inside the PC. When the PC is fully off,
  JARVIS is off (see Section 9).
- In online mode JARVIS depends on an internet connection and an AI API.
- In offline mode JARVIS uses smaller local models: it is slower and
  less capable, especially in Urdu and for complex tasks (Section 10).
- AI answers can be wrong; important actions need confirmation.
- Cloud AI has an ongoing usage cost (Section 17).
- The result is a capable personal agent, not a movie-style AI.

6. CORE SYSTEM COMPONENTS

6.1 AI BRAIN

Responsible for:
- Understanding user requests
- Reasoning about tasks
- Selecting tools
- Producing responses
- Coordinating multi-step tasks

The AI brain is the central decision-making layer.

It must NOT directly have unlimited system access. It requests actions
through controlled tools, and every tool call passes through the
security layer first.

6.2 MODEL STRATEGY

Free cloud models are acceptable for plain chat (Phases 1-2). They are
rate-limited and often unreliable at tool/function calling.

Rules:
- From Phase 3 onward, the model used for tool calling must be tested
  for reliable function calling BEFORE it is adopted.
- Keep a configurable model list in .env (primary + fallbacks) so models
  can be changed without code edits.
- Separate "chat model" from "tool-calling model" if needed.
- Log which model handled each request (without logging secrets).
- Vision (Phase 7) requires a vision-capable model; choose it then.
- Local models (Phase 11) are tested separately; if a local model cannot
  call tools reliably, offline mode limits itself to safe built-in
  commands (Section 10).

6.3 VOICE INPUT

Purpose: Convert the user's speech into text.

Example:

User says: "Jarvis, open Visual Studio Code."

Voice: -> Speech-to-Text -> "Jarvis, open Visual Studio Code."

Current behavior: recognized text appears in the editable message box so
the user can review it before sending. Language is selectable (English,
Urdu, Hindi).

Known limitation: browser recognition depends on the browser's online
recognition service and a working network, and quality for Urdu varies.
Roman Urdu (Urdu written in English letters) is NOT a recognition
language: the user can speak Urdu or Hindi, or type Roman Urdu, and the
AI can be told to reply in Roman Urdu.

Barge-in: if the user starts speaking (or presses the mic/hotkey) while
JARVIS is talking, JARVIS stops speaking immediately.

6.4 VOICE OUTPUT

Purpose: Convert JARVIS responses into speech.

Current behavior: uses device-installed system voices (works offline),
with voice selection, preview and a saved preference. It does not
generate or clone voices. A voice toggle must be able to fully suppress
playback.

Example:

AI response: "Certainly. Opening Visual Studio Code."

    -> Text-to-Speech
    -> Speaker

6.5 TOOL SYSTEM

JARVIS will have controlled tools. Every tool must define:
- name and purpose
- input schema (validated)
- risk level (LOW / MEDIUM / HIGH)
- whether it works offline (YES / NO)
- what it logs
- a test

Examples:

System: open_app(), close_app(), get_system_status(), volume_control(),
lock_pc(), sleep_pc(), restart_pc(), shutdown_pc()

Window/clipboard: list_windows(), focus_window(), minimize/maximize,
read_clipboard(), write_clipboard()

Media: play/pause, next/previous, mute

Files: read_file(), create_file(), write_file(), create_folder(),
list_directory()

Browser: open_url(), search_web(), navigate()

Coding: inspect_project(), run_command(), run_tests(), git_status()

Utilities: calculator(), time(), weather(), set_timer(), set_alarm(),
set_reminder()

6.6 MEMORY

Memory allows JARVIS to remember useful information.

Examples:
- Preferred applications
- Frequently used project folders
- User instructions
- Important non-sensitive preferences
- Useful conversation context

Initial implementation: SQLite (local, works offline).

Future: PostgreSQL + vector/semantic memory if required.

Memory rules:
- Only save what the user explicitly asks to remember, or clearly
  non-sensitive preferences after the user approves.
- Never store passwords, API keys, banking details, OTP codes or
  similar secrets.
- The user can list, edit and delete every memory.
- A "forget everything" option must exist.

6.7 VISION

JARVIS will eventually be able to inspect screenshots or supported
visual input.

Example:

User: "Jarvis, what's wrong on my screen?"

Process:
1. Capture/receive screen image
2. Send image to a vision-capable AI
3. Analyze UI/error
4. Explain problem
5. Suggest or perform approved action

Privacy rule: screenshots are captured only on user request, never
continuously, and are not stored unless the user chooses to save them.

Vision needs a vision-capable model. Offline vision requires a local
vision model and strong hardware; it is optional and NOT required for
offline mode.

6.8 WEB ACCESS

JARVIS should eventually be able to:
- Search the web
- Find current information
- Read relevant pages
- Summarize results
- Answer questions using current information

For time-sensitive questions, current web information should be
preferred over old memory. Answers should show their sources. Web
access is an online-only feature.

6.9 CONVERSATION STORAGE

Decision: conversation history is kept in the current session by
default. Persistent history (SQLite) is added in Phase 6 together with
memory, with a clear-history option. Until then, nothing is saved to
disk except user settings (such as the selected voice and language).

6.10 LANGUAGE SUPPORT

Done: English, Urdu and Hindi for speech recognition and for AI
response language.

Planned: Roman Urdu replies (AI language option) and typed Roman Urdu
understanding. Speech recognition in Roman Urdu is not available and is
not planned.

Offline note: small local models and local STT are weaker in Urdu than
in English. Offline accuracy for Urdu/Hindi must be measured and
recorded (Phase 11).

6.11 NO-INTERNET BEHAVIOR

JARVIS must never crash or hang when the internet drops.
- It detects the loss of connection (Phase 11 formalizes this; until
  then it shows a clear error message).
- It tells the user plainly: "No internet. I can still do local tasks."
- Local-only tools keep working (open apps, folders, system status,
  volume, timers, power control, file reading, calculator, time).
- Online-only tools (web search, weather, cloud AI) say they are
  unavailable instead of failing silently.
- When the connection returns, JARVIS switches back automatically (or
  asks, depending on the setting).

6.12 TIMERS, ALARMS AND REMINDERS

- set_timer("10 minutes"), set_alarm("7:00"), set_reminder("call
  Ahmed at 5 pm").
- Stored locally (SQLite) so they survive restart. They work offline.
- When one fires: dashboard notification + spoken message + Windows
  notification.
- Limits: reminders only fire while JARVIS is running; if the PC is off
  or asleep they fire late when the PC wakes (they are not a substitute
  for a phone alarm). For wake-up alarms use the Windows Clock app or a
  phone.

7. SECURITY MODEL

Security is a major part of the project and is built BEFORE any tool
that can change the computer (Phase 3, step 3A).

JARVIS will NOT be given unrestricted permission to do anything
silently.

Actions are categorized.

LOW RISK:
- Open an application
- Search the web
- Read a non-sensitive file
- Check system status
- Change volume, set a timer

These can normally execute automatically.

MEDIUM RISK:
- Modify project files
- Install packages
- Run development commands
- Lock the PC, put it to sleep
- Close applications

Depending on the action, JARVIS may execute or request confirmation.
Default: ask for confirmation unless the user has allowed it for that
project or action.

HIGH RISK:
- Delete important files
- Delete folders
- Shut down or restart the PC
- Send emails/messages
- Change important system settings
- Execute potentially destructive commands
- Perform financial or account actions

These always require explicit confirmation.

Example:

JARVIS: "This action will permanently delete the selected folder.
Continue?"

User: "Yes."

Only then should the action execute.

PIN / PASSPHRASE FOR SENSITIVE ACTIONS

Problem: a voice "yes" can be said by anyone near the microphone (or
heard from a video/TV). So for HIGH risk actions a voice "yes" alone is
not enough.

Rule:
- HIGH risk actions require a PIN or passphrase, typed in the dashboard
  (or a click on the confirmation dialog while the dashboard is
  focused).
- The PIN is stored only as a salted hash, never as plain text.
- After several wrong attempts JARVIS locks sensitive actions for a
  period of time and logs the attempts.
- The user can choose which actions need the PIN (default: all HIGH).

Technical safeguards (to implement in Phase 3A):
1. Allowlist: tools can only run actions from an approved list; unknown
   commands are refused.
2. Path rules: file tools can only touch approved folders; system
   folders (Windows, Program Files) are blocked.
3. Command rules: no raw shell by default; destructive patterns (for
   example recursive delete, format, registry edits) are blocked or
   forced to HIGH risk.
4. Confirmation flow: the confirmation request shows exactly what will
   happen; confirmations expire after a short time; a confirmation
   applies to ONE action only.
5. Prompt-injection defense: text from web pages, files or screenshots
   is treated as data, never as instructions. It can never approve an
   action or change security rules.
6. Audit log: every tool call (time, tool, arguments summary, risk
   level, confirmed or not, result) is written to the log.
7. Emergency stop: a visible STOP control cancels the running task.
8. Rate/step limits: a maximum number of tool calls per task, to prevent
   runaway loops.
9. Local-only server: the backend listens ONLY on 127.0.0.1 (this
   computer), never on the network, and accepts requests only from the
   JARVIS dashboard (CORS restricted). Nobody else on the Wi-Fi can
   talk to it. Any future remote access (Section 22) needs its own
   authentication design first.
10. Single instance: only one JARVIS backend can run at a time.

8. HOW TO RUN AND USE JARVIS

8.1 Daily use (current and until Phase 10)

1. Double-click start_jarvis.bat.
   - It starts the backend, starts the frontend and opens the dashboard
     in the browser (for example http://localhost:3000).
2. Wait for the dashboard to show "Backend: online" and the model name.
3. Type a message, or press the microphone button and speak.
4. To stop: close the dashboard and run stop_jarvis.bat (or close the
   console windows).

8.2 Later (Phase 9 and 10)

- Phase 9: decision whether JARVIS stays a browser dashboard or becomes
  a desktop window (Tauri/Electron) with tray icon and a global hotkey
  (for example Ctrl+Space = start listening).
- Phase 10: "Start with Windows" option. JARVIS starts in the
  background after you sign in; the dashboard opens from the tray icon
  or hotkey. A wake word ("Jarvis") is optional and can be turned off.

8.3 What the user sees on screen

- Central JARVIS orb: idle / listening / thinking / speaking
- Conversation (user and JARVIS)
- Microphone indicator (clearly shows when the mic is active)
- Online / Offline indicator and the current model name
- CPU / RAM and backend status
- Current task and tool activity (for example "Opening VS Code...")
- Confirmation dialog for risky actions (with PIN field when needed)
- STOP button to cancel the running task
- Notifications for timers, alarms and reminders

8.4 Limitation of the browser microphone

Browser speech recognition works only while the dashboard tab/window is
open and focused enough to listen. For "always listening" use, JARVIS
needs the desktop app (Phase 9) and/or backend speech-to-text (Phase 2C
and Phase 10 wake word).

8.5 Troubleshooting (keep this list updated)

- Dashboard says "Backend offline": start_jarvis.bat did not start the
  backend. Check the backend console window for errors; check that the
  .env file exists and the virtual environment is active.
- Port already in use: another copy of JARVIS is running. Run
  stop_jarvis.bat, then start again.
- No voice reply: check the voice toggle, the selected voice, and the
  Windows volume.
- Microphone not working: allow microphone permission in the browser;
  check the Windows privacy settings for the microphone; test in
  Chrome/Edge (not an embedded preview browser).
- Recognition network error: browser recognition needs internet. Wait
  for the connection, or use local speech-to-text once it is added.
- Model rate limit: JARVIS falls back to the next model; if all are
  limited, wait and retry or choose another model.
- Offline and nothing answers: local models are not set up yet
  (Phase 11), so AI chat needs internet until then.

9. POWER CONTROL AND WAKING THE PC

9.1 Turning the PC off, restarting, sleeping, locking

JARVIS can do this through power tools (Phase 3):
- lock_pc()        MEDIUM risk
- sleep_pc()       MEDIUM risk
- restart_pc()     HIGH risk (confirmation + PIN)
- shutdown_pc()    HIGH risk (confirmation + PIN)

Before shutdown or restart JARVIS warns: "Unsaved work may be lost.
Continue?" and may offer a short delay with a cancel option.

9.2 Turning the PC ON: what is and is not possible

JARVIS is a program running inside the PC. When the PC is completely
off (or asleep), JARVIS is not running and cannot listen, so JARVIS
CANNOT turn the PC on by itself. "Jarvis, wake up" cannot power on a
switched-off computer.

Real ways to turn the PC on:
1. Power button (simplest, most reliable).
2. Scheduled wake: Windows Task Scheduler (wake from sleep/hibernate)
   or the BIOS/UEFI "RTC alarm / power on by alarm" setting (for
   example every day at 8:00).
3. Wake-on-LAN: send a "magic packet" from another device (phone or
   another computer on the same network). Requires BIOS support and
   normally a LAN cable; often does not work on Wi-Fi laptops.
4. Mobile companion app that sends Wake-on-LAN (future, Section 22).

Documented here so nobody expects JARVIS to "boot" the machine.

9.3 After the PC starts

If "Start with Windows" is enabled (Phase 10), JARVIS starts by itself
after sign-in and is ready within seconds. Without it, run
start_jarvis.bat.

10. OFFLINE AND HYBRID MODE

Goal: JARVIS should still be useful without internet, and should use
the cloud only when it is available and needed.

10.1 Three modes

ONLINE   - cloud AI model + web search + cloud/browser speech
           (best quality)
OFFLINE  - local AI model + local speech-to-text + local text-to-speech
           + local tools only
HYBRID   - (default recommended) uses online when internet is
           available, switches to offline automatically when it drops,
           and switches back when it returns. The user can also force
           ONLINE or OFFLINE in settings (for privacy or to save cost).

10.2 What works offline

Works offline:
- Dashboard UI (all assets bundled locally)
- System voices (text-to-speech)
- Local speech-to-text (after Phase 2C/11: faster-whisper or similar)
- Local AI chat with a small model (Ollama/llama.cpp)
- Open/close apps, folders, files, system status
- Volume, media, window and clipboard control
- Power control (lock, sleep, restart, shutdown)
- Timers, alarms, reminders
- Calculator, time
- Files and coding tools (read/edit files, git status, run tests)
- Memory and conversation history (SQLite)
- Security layer, PIN, logs, backups

Does NOT work offline:
- Web search, current news, weather
- Cloud AI models (better reasoning and tool-calling)
- Browser-based speech recognition
- Playwright web automation
- Cloud-only vision models
- Downloading or updating models and packages

10.3 Honest limitations of offline mode

- Local models that run on a normal laptop (about 3B to 8B parameters)
  are noticeably weaker than cloud models: simpler answers, more
  mistakes, weaker Urdu/Hindi.
- Tool calling on small local models can be unreliable. Rule: if a
  local model fails the tool-calling tests, offline mode uses a built-in
  "command matcher" (fixed commands such as "open Chrome", "volume
  down", "lock the PC", "set a timer for 10 minutes") instead of letting
  the model improvise actions. Multi-step agent tasks (Phase 8) are
  ONLINE-ONLY unless local tests prove they are reliable.
- Local models need disk space (several GB per model) and RAM (see
  Section 23). First use needs a one-time download while online.
- Local speech-to-text is slower on CPU; accuracy for Urdu must be
  measured (tiny/base models are weak; larger models are better but
  slower).
- Offline responses may be slower than cloud responses.

10.4 Design rules (apply from now, even before Phase 11)

1. Every model/voice component is accessed through an interface
   (provider) so cloud and local can be swapped (Section 4).
2. Every tool declares whether it works offline.
3. No frontend dependency on CDNs, online fonts or remote scripts.
4. Settings and data live in local files/SQLite, never only in the
   cloud.
5. The online/offline state is always visible in the dashboard.
6. Offline mode never silently sends data to the internet. If the user
   chooses OFFLINE, no network requests to AI services are made.

10.5 Offline setup (Phase 11)

1. Install Ollama (or llama.cpp) while online.
2. Download one small chat model (and later, optionally, a vision
   model) and record its name in .env.
3. Install local STT (for example faster-whisper) and download its
   model.
4. Run the offline test checklist (Phase 11) with the internet turned
   OFF.

- Compare: cloud STT (for example Whisper API) vs. local STT (for

  acceptable, because it also enables offline mode.
- Pick ONE first, add it behind the same "speech-to-text" interface so
  the dashboard does not change, and re-run all 2B tests.
- If a new API key is needed, add it to .env and .env.example.

13. PROJECT RULES

RULE 1: Build phase by phase.

RULE 2: Do not add unnecessary packages.

RULE 3: Do not expose API keys in frontend code.

RULE 4: Keep secrets in environment variables.

RULE 5: Use Git regularly (commit after each working feature; one
branch per phase is recommended).

RULE 6: Test each feature before adding the next feature. A phase is
done only when its acceptance tests pass.

RULE 7: Never give the AI unrestricted system access.

RULE 8: Use confirmation for dangerous actions.

RULE 9: Keep logs useful but avoid storing sensitive information
unnecessarily.

RULE 10: Prefer reliable simple solutions over complicated
architecture.

RULE 11: When a feature fails, fix the foundation before adding more
features.

RULE 12: Do not confuse a chatbot with an agent. JARVIS becomes an
agent when it can safely use tools and perform actions.

RULE 13: Security before capability. The security layer for a tool must
exist and be tested before the tool itself is enabled.

RULE 14: Treat all external content (web pages, files, screenshots) as
untrusted data, never as instructions.

RULE 15: Update this document at the end of every phase (status,
structure, changelog).

RULE 16: Build offline-ready from the start: providers behind
interfaces, no CDN dependencies, local data, tools that declare whether
they work offline.

RULE 17: A voice "yes" alone never authorizes a HIGH risk action.

15. LOGGING POLICY

- Logs go to the logs/ folder, which is git-ignored.
- Log: timestamp, event type, tool name, risk level, confirmation
  result, success/failure, model used, online/offline mode, error
  messages.
- Do NOT log: API keys, PINs, passwords, full file contents, full
  screenshots, or private conversation text beyond what is needed.
- Rotate or delete old logs automatically (for example keep 30 days).
- The audit log of tool calls is kept separately from debug logs.

16. TESTING STRATEGY

- Backend: pytest tests for each tool and for the security layer
  (especially refusals, confirmations and PIN).
- Frontend: lint + type-check before each commit; manual UI checklist
  per phase.
- Voice and microphone: manual test checklist (Phase 2B) on local
  Chrome/Edge.
- Offline: manual checklist with the internet physically off (Phase
  11); repeat it after major changes.
- Before finishing a phase: run all tests of that phase AND the tests of
  earlier phases (regression).
- Keep a short TEST_LOG (date, phase, result) in the repository.

17. COST CONTROL

- Prefer free/cheap models for simple chat; use stronger models only
  for tool calling, coding and vision.
- Set a monthly usage limit on every API key.
- Limit the conversation history sent to the model (summarize or trim
  old messages).
- Limit tool-call and retry counts per task (Phase 8).
- Vision and web search cost more: use them only on request.
- Offline/local mode has no API cost (only electricity and hardware).
- Show usage/cost information in the dashboard (Phase 9-10).

18. PERFORMANCE TARGETS

Targets to aim for (measure and adjust to the real hardware):
- Dashboard starts (after start_jarvis.bat) in under 30 seconds.
- Local command (open app, volume) completes in under 1 second after
  the text is received.
- Cloud AI: first words of the reply within about 3 seconds in normal
  conditions.
- Speech-to-text result within about 2 seconds after the user stops
  talking (cloud); local STT target to be measured and recorded.
- Local model: first words within about 5 to 10 seconds on a normal
  laptop (to be measured).
- JARVIS idle uses little CPU and a modest amount of RAM; record the
  numbers in the test log.
- Animations stay smooth and never block commands.

Updates and versioning:
- Version number shown in the dashboard and in logs.
- Database changes use migrations so old data keeps working after an

- Update process: commit/tag in Git, backup, update, run tests, verify

- Keep a short changelog in the repository.

Packaging (only when needed, for example another PC):

21. RISKS AND MITIGATIONS

- Wrong or invented AI answers -> show sources (Phase 5), confirm
  important actions, keep the user in control.
- Destructive actions by mistake -> risk levels, confirmations, PIN,
  path and command rules, backups/Git.
- Someone else speaking near the microphone -> PIN for HIGH risk
  actions, no voice-only approval (Rule 17).
- Prompt injection from web/files/images -> Rule 14.
- Free model rate limits/outages -> fallback chain, clear error
  message, option to switch model, offline mode (Phase 11).
- Speech recognition errors, especially Urdu -> editable text before
  sending, STT fallback (Phase 2C).
- Weak local models acting wrongly offline -> command matcher, no
  autonomous HIGH risk actions, offline agent tasks disabled by
  default.
- API key leak -> .env rules, usage limits, rotate immediately.
- Backend reachable by others on the network -> bind to 127.0.0.1 only,
  CORS restriction.
- Privacy of microphone/screen -> clear indicators, on-request capture
  only, no hidden recording.
- Local models too slow on this laptop -> choose smaller models, record
  measurements, keep cloud as the main mode.
- Over-building too early -> Rules 1, 6 and 11.

23. HARDWARE PLAN

Initial development: No laptop upgrade is required.

Cloud AI approach:
- Normal Windows laptop is sufficient.
- CPU/GPU does not need to be powerful for most AI API operations.
- Internet connection is important.

Local/offline approach (Phase 11):
- Small models (about 3B parameters, quantized): usually workable with
  8 GB RAM, slow on CPU.
- Better models (7B-8B): 16 GB RAM recommended; a GPU makes responses
  much faster.
- Local speech-to-text: small/base models run on CPU; larger models
  (better for Urdu) are slower and benefit from a GPU.
- Disk: allow roughly 5 to 20 GB for local models.
- These are rough guides. Test on the real laptop before buying
  anything.

Possible future hardware considerations:
- 16 GB RAM or more
- Fast SSD
- Strong CPU
- NVIDIA GPU with suitable VRAM for local models

Do NOT upgrade hardware before testing the actual project requirements.
